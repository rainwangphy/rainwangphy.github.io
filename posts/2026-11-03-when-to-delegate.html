Delegative Recursive Self-Improvement

委派式递归自我改进

How agents can turn experience into executable capabilities—and use them to improve how they build the next ones.

将任务经验转化为可执行能力，再用这些能力改善后续能力的构建。

  • agents
  • delegation
  • recursive self-improvement

Suppose a strong language model solves a problem today, then encounters a thousand more instances governed by the same rules tomorrow. What should remain after the first few successes? A useful outcome would be a reliable program that can handle the next instance without asking the agent to work through the whole problem again. A more ambitious outcome would be a capability that also helps the system build its next program.

This is the idea I call Delegative Recursive Self-Improvement, or Delegative RSI. An agent initially explores and solves tasks, then progressively converts the stable parts of its work into reusable executable mechanisms. The strong agent remains available for unfamiliar problems, supervision, and necessary intervention.

Delegative Recursive Self-Improvement (Delegative RSI)

A paradigm of recursive self-improvement in which an intelligent system progressively transforms its own task-solving processes into reusable mechanisms that can execute within a defined scope without continuous involvement from the originating agent. Through repeated execution, verification, and refinement, these mechanisms reduce reliance on costly reasoning and become building blocks for constructing, validating, and improving further delegations. This feedback loop enables the system to improve both its task-solving capabilities and its capacity to develop new executable capabilities.

The definition describes a proposed mechanism of improvement. Whether a particular system realizes those benefits is an empirical question. The key hypothesis is that accumulated executable capabilities can improve the process by which further capabilities are developed.

IFrom successful execution to a reusable capability

Consider an agent preparing a recurring experimental report. On its first attempt, it may inspect unfamiliar files, clarify the required statistics with a person, write analysis code, produce figures, and repair mistakes. Completing the report is already useful. The next opportunity is to turn the stable parts of that work into a procedure that accepts new data.

One successful run rarely establishes the full procedure. Repeated execution reveals which decisions depend on the input, which rules remain fixed, and where exceptions arise. The system can then parameterize the workflow, add input checks and error handling, and evaluate it on independent cases before allowing it to take over.

  1. Solve: use the strong agent, with human guidance where needed, to complete unfamiliar tasks.
  2. Extract: identify reusable rules and separate them from instance-specific choices.
  3. Validate: test or prove the candidate’s behavior within a stated scope.
  4. Delegate: route suitable future instances to the executable mechanism.
  5. Refine: use failures and changed requirements to revise, replace, or retire it.

A delegate here is a program or workflow with a defined input contract, expected outputs, dependencies, and an acceptance procedure. A recorded execution trace alone does not supply those guarantees. For suitable tasks, the deployed component can be the resulting program; the full agent does not have to remain in every execution path.

IISupervision without repeating all the reasoning

Independent execution is relative to a scope. A reporting program may handle a documented schema while rejecting unknown units or missing fields. A rejected input can return to the strong agent for diagnosis. That intervention may produce a one-off answer, a repaired delegate, or a newly recognized task family.

LayerResponsibility
ExecutionRun validated delegates on inputs within their supported scope.
Routing and checkingCheck applicability and outputs; escalate unresolved cases.
Strong agentSolve unfamiliar tasks and construct, repair, or extend delegates.

Human involvement can establish the initial specification and review uncertain cases. As evidence accumulates, routine execution may need less intervention. The goal is to concentrate expensive reasoning where it adds value.

Supervision has to be included in the cost. If a strong agent fully resolves every instance to check the delegate, much of the saving disappears. Input constraints, assertions, exact checkers, and inexpensive monitors can handle some obligations. Their limits must be explicit: a monitor may miss a semantic change, and passing tests does not establish correctness for every possible input.

IIIWhat makes the improvement recursive?

Accumulating useful programs improves a system’s available capabilities. The stronger recursive claim is that these capabilities improve how the system constructs subsequent capabilities. The distinction matters: a growing folder of scripts is not sufficient evidence that the improvement process itself has improved.

In the reporting example, a validated parser can become a component of a new analysis workflow. A reusable comparison tool can check a new implementation against a reference. A test-generation procedure can help expose errors in future delegates. Each can reduce part of the effort of building and validating the next capability, provided its assumptions remain valid in the new use.

Solve tasks → extract and validate delegates
     ↑                         ↓
Build new capabilities ← reuse delegates
                         in construction and checking

The learning occurs at the system level: the library, routing rules, validators, and construction procedures can change even while the underlying model’s weights remain fixed. A stronger version could also learn a cheaper program synthesizer from accumulated task–program pairs.

The operational test for recursion is whether earlier delegations improve the cost, reliability, or scope of constructing later ones. Better performance on repeated instances establishes reuse; improvement in subsequent capability construction establishes the additional feedback this proposal is about.

This does not imply unlimited or accelerating improvement. Reuse can introduce incompatible assumptions, validation can remain expensive, and a larger library can become harder to search and maintain. Versioning, revalidation, replacement, and retirement belong inside the loop.

IVWhich tasks can enter the loop?

The foundation remains the question of delegability. Task difficulty is not delegation difficulty. Finding a shortest path in a large graph with nonnegative edge weights may involve substantial computation, yet the solving rule is explicit and reusable. Classifying a few short messages under a newly invented, ambiguous policy may require much less execution but be harder to turn into a reliable program.

We need to distinguish understanding a task, finding its solution procedure, and executing that procedure. Compilation can remove repeated reasoning about the procedure; it does not automatically reduce the intrinsic cost of the underlying computation.

There are also two capability boundaries. Existence asks whether a compact, accurate, efficient delegate exists in the permitted program space. Learnability asks whether a synthesis system can discover it from the available specification and examples within budget. A short program can embody an insight that is difficult to discover.

Examples may also underdetermine the intended task. Several programs can agree on every observed case and disagree on the next one. More synthesis effort alone cannot resolve a missing requirement. Human clarification may be necessary before the system can establish what to delegate.

DimensionQuestion
CompressibilityCan the required behavior be expressed as a compact, reusable program?
SynthesizabilityCan that program be generated from the specification and examples?
VerifiabilityCan correctness be established, or error estimated, at acceptable cost?
Distribution stabilityDoes the program remain valid under expected changes, and can changes requiring revision be identified?

The first two dimensions separate an expressible solution from a discoverable one. Compactness alone is insufficient: the delegate must meet execution and accuracy constraints. Verification determines the evidence for accepting it, while stability determines how long that investment remains useful.

VA frontier that moves with experience

Instance novelty changes the input while preserving the solving rule. Task novelty changes the rule, abstraction, or solution method. A fixed delegate may handle many unfamiliar instances while failing after a small change in the task’s meaning.

Novelty is relative to the system’s abstraction library. With a suitable general solver, a new constraint may become an ordinary input. Without that solver, the system may need a new algorithm or implementation. A component that supports one task can therefore change the difficulty of constructing delegates for others.

The delegability frontier describes which tasks a system can reliably delegate under given resource and accuracy constraints. Delegative RSI asks how this frontier changes as the system solves tasks and reuses the resulting capabilities in further development.

The frontier need not move outward everywhere. Changed task rules or external interfaces can invalidate existing delegates. A system must recognize when its accumulated evidence no longer applies. A claim of progress should account for capabilities that were lost or became more expensive to maintain.

VILearning to construct delegations

One possible implementation is learned delegation. A strong language model produces candidate task–program pairs. After validation and filtering, those pairs train a smaller neural compiler that maps specifications and examples to executable delegates. The compiler’s outputs still require an acceptance procedure.

This offers two levels of amortization. At the instance level, a program replaces repeated reasoning on the same task. At the task level, a learned compiler reuses experience from program discovery across tasks. Reusable components and validators can support that second level even before any compiler is trained.

A learned compiler is therefore one route to Delegative RSI, rather than a prerequisite. The central requirement is the feedback from accumulated capabilities into subsequent capability construction. Model training can strengthen that feedback, but its contribution should be measured separately from improvements due to tools and libraries.

Success on familiar templates would establish only a limited form of transfer. New compositions, rule systems, and task families provide stronger tests. When synthesis or validation fails, the system can return to the strong agent; those calls remain part of its measured cost.

VIIWhen does delegation pay?

A correct delegate can still be a poor investment for a task that appears once. Let G be its generation and initial validation cost, E its execution cost per instance, L the direct strong-agent cost per instance, and N the number of instances served before revision.

Direct reasoning:  N × L
Basic delegation:  G + N × E

Basic break-even condition:
N × (L − E) > G

The costs must use comparable units and refer to systems meeting the same reliability requirement. To evaluate an operational system, also include per-instance routing and checking cost O, expected fallback cost per instance F, and maintenance cost M over the reuse window:

Total delegation cost:
G + N × (E + O + F) + M

Here F includes the frequency and cost of fallback calls, and M excludes validation already counted in G. The direct baseline must likewise include its necessary checks and retries. Compiler training and shared-library construction require accounting across the tasks they serve.

Recursive improvement could reduce future generation or validation costs, improve reliability at fixed cost, or make additional task families feasible. These are separate outcomes. A reduction in strong-model calls alone does not establish that the full system is cheaper or more capable.

VIIITesting the recursive claim

A useful starting point is a controlled sequence of task families with known reference programs. Vary program structure, specification completeness, execution cost, and novelty relative to the available library. Reference programs establish existence in the tested setting; synthesis difficulty must still be measured through the success rates and budgets of specified synthesizers.

The original delegation comparison remains useful: strong-agent direct execution, strong-model-generated delegates, and delegates generated by a smaller learned compiler. To test recursion, add a comparison between systems allowed to reuse their delegates only for execution and systems also allowed to use them in constructing and validating new delegates.

Those systems should begin with the same model, initial tools, task sequence, and resource accounting. At checkpoints, evaluate on held-out tasks using a fixed construction budget. Compare a frozen initial library, accumulated delegates available only for execution, and the full feedback loop. Ablations of reusable validators and construction tools can help identify which components produce an improvement.

Separate new instances of known tasks, unseen compositions, and tasks requiring held-out rules or abstractions. Inputs used to select or repair programs must stay separate from final evaluation. If compiler training is added, report it as a distinct experimental condition.

Measure delegated task coverage, accuracy, generation and validation cost, execution and supervision cost, fallback frequency, human intervention, and maintenance. Most importantly, measure the cost and success rate of constructing delegates for new tasks as prior experience accumulates. Repeated runs and varied task orders would help distinguish a durable effect from a favorable sequence.

Evidence for Delegative RSI would be an improvement in later capability construction attributable to the reusable mechanisms, after accounting for their full cost. If only repeated-instance execution improves, we have demonstrated useful delegation. If construction does not improve, the stronger recursive claim remains unsupported.

IXWhat remains for the strong agent?

The strong agent can progressively focus on discovering abstractions, resolving unfamiliar cases, and improving the mechanisms that handle routine work. Its role shifts as the system’s reliable executable capabilities grow. No claim that every task can be compiled is required.

Some tasks change too quickly to repay synthesis. Others lack a sufficiently clear specification, an affordable checker, or a suitable abstraction. These remain reasons to involve the strong agent or a person, and their involvement still needs appropriate evidence of success.

The question that began as “When to delegate?” becomes a question about how a system develops: can it turn experience into dependable executable capabilities, then use those capabilities to improve how it builds the next ones? Delegative RSI names that proposed feedback loop. Its promise should be judged by the reliable task coverage it enables and the full cost of getting there.

假设一个强语言模型今天解决了一个问题，明天又遇到一千个遵循同样规则的新实例。最初几次成功之后，系统应该留下什么？一种有价值的产物，是一个可靠的程序，让下一个实例不必再由智能体完整推理一遍。更进一步，这个程序还可以帮助系统构建下一个程序。

我把这个想法称为委派式递归自我改进，英文为 Delegative Recursive Self-Improvement，简称 Delegative RSI。智能体最初负责探索和求解任务，随后逐步把工作中稳定的部分转化为可复用的执行机制。强智能体则继续负责陌生问题、监督与必要的干预。

委派式递归自我改进的定义

一种递归自我改进范式：智能系统逐步将自身的任务求解过程转化为可复用的机制，使这些机制能够在明确的适用范围内执行，而无须原智能体持续参与。通过反复执行、验证与改进，这些机制降低了系统对高成本推理的依赖，并成为构建、验证和改进后续委派机制的基础组件。这一反馈闭环使系统既能改善任务求解能力，也能提升开发新可执行能力的能力。

这个定义描述的是一种拟议的改进机制。具体系统能否实现这些收益，仍然需要实验回答。核心假设是：积累的可执行能力，可以进一步改善后续能力的开发过程。

一从成功执行到可复用能力

考虑一个定期生成实验报告的智能体。第一次执行时，它可能需要检查陌生的数据文件，向人确认统计要求，编写分析代码，生成图表，并修正错误。完成报告已经有价值；接下来的机会，是把其中稳定的部分转化为能够接收新数据的程序。

一次成功通常不足以确立完整的求解过程。反复执行会逐渐暴露哪些决策依赖输入，哪些规则保持不变，以及哪里会出现例外。系统由此可以将工作流参数化，加入输入检查和异常处理，并在独立样例上评估，再让程序接管相应任务。

  1. 求解：由强智能体完成陌生任务，必要时接受人的指导。
  2. 提取：识别可复用规则，将它们与具体实例的选择区分开。
  3. 验证：在明确的适用范围内，测试或证明候选程序的行为。
  4. 委派：把后续符合条件的实例交给可执行机制。
  5. 改进：根据失败和需求变化，修改、替换或淘汰已有机制。

本文所说的 delegate（委派程序），是一个具有明确输入约定、预期输出、依赖条件和验收方式的程序或工作流。单纯保存一次执行轨迹，并不能提供这些保证。对于合适的任务，最终部署的可以是生成的程序，无须让完整的智能体持续参与每一次执行。

二监督如何避免重复全部推理？

独立执行总是相对于适用范围而言的。一个报告程序可以处理文档中规定的数据格式，同时拒绝未知单位或字段缺失的输入。被拒绝的输入可以交回强智能体诊断。这次干预可能产生一个临时答案、一个修复后的程序，或者一个新识别出的任务家族。

层次主要职责
执行层使用经过验证的委派程序，处理适用范围内的输入。
调度与检查层检查适用条件与结果，将无法解决的情况交给上层处理。
强智能体层求解陌生任务，构建、修复或扩展委派程序。

人可以参与确定最初的任务规格，并审查不确定的情况。随着证据积累，常规执行可能逐渐减少干预。目标是让昂贵的推理集中在能够产生价值的地方。

监督本身必须计入成本。如果强智能体为了检查程序而把每个实例完整重做一遍，大部分收益就会消失。输入约束、程序断言、精确检查器和低成本监控可以承担一部分检查义务，但也需要明确它们的局限：监控可能遗漏语义变化，通过测试也不意味着对所有可能输入都正确。

三改进的递归性在哪里？

积累有用的程序，可以增加系统已经具备的能力。更强的递归主张是：这些能力进一步改善了系统构建后续能力的过程。这一区别很重要；脚本文件夹越来越大，本身不足以证明改进过程也得到了改善。

在实验报告的例子中，经过验证的解析器可以成为新分析流程的组件；可复用的比较工具可以检查新实现与参考结果是否一致；测试生成程序可以帮助发现未来委派程序中的错误。只要原有假设在新用途下仍然成立，它们就可能降低构建和验证下一项能力所需的部分投入。

求解任务 → 提取并验证委派程序
   ↑                  ↓
构建新能力 ← 在构建与检查中复用已有程序

学习发生在系统层面：即使底层模型的权重不变，程序库、调度规则、验证器和构建过程仍然可以改变。更进一步的版本，也可以利用积累的任务—程序配对，训练成本更低的程序合成模型。

检验递归性的实际标准，是早期的委派能否改善后续委派的构建成本、可靠性或覆盖范围。重复实例上的表现提升，说明复用有效；后续能力构建过程的改善，才体现了这里提出的额外反馈。

这不意味着改进会无限持续或不断加速。复用可能引入不兼容的假设，验证可能依然昂贵，更大的程序库也可能更难检索和维护。版本管理、重新验证、替换和淘汰，都属于这个闭环。

四哪些任务能够进入这个闭环？

基础仍然是可委派性。任务难度不等于委派难度。在边权非负的大图中寻找最短路径，可能需要大量计算，但求解规则明确且可复用。根据一套刚提出、含义模糊的规则，对几条短消息分类，执行规模可能很小，却更难转化为可靠的程序。

需要区分理解任务、发现求解过程和执行求解过程。编译能够消除围绕求解过程的重复推理，却不会自动降低底层计算本身的固有成本。

这里还有两种能力边界。存在性问的是：在允许的程序空间内，是否存在简洁、准确且高效的委派程序？可学习性问的是：合成系统能否根据现有规格与示例，在预算内发现它？一个很短的程序，也可能凝结了难以发现的洞见。

示例也可能不足以确定任务原意。多个程序可以在全部已观察样例上达成一致，却在下一个输入上产生分歧。单纯增加合成投入，无法补全缺失的需求。系统可能需要先向人澄清，再确立应该委派什么。

维度要回答的问题
可压缩性
Compressibility		任务要求的行为，能否被表达为简洁、可复用的程序？
可合成性
Synthesizability		能否根据任务规格和示例，生成这个程序？
可验证性
Verifiability		能否以可接受的成本确立正确性，或估计错误率？
分布稳定性
Distribution stability		程序在预期变化下是否仍然有效？需要修改的变化能否被识别？

前两个维度区分了解法能否被表达，以及能否被发现。简洁本身并不充分：程序还必须满足执行效率与准确率要求。验证决定了接受它的证据，稳定性则决定了这笔投入能够持续产生多久的收益。

五一条随经验移动的能力边界

实例新颖性改变输入，但保留求解规则。任务新颖性改变规则、抽象结构或求解方法。一个固定程序可以处理大量陌生实例，却可能因为任务含义的细微变化而失效。

新颖性是相对于系统拥有的抽象与算法组件库而言的。有了合适的通用求解器，新约束可能只是普通输入；没有时，系统可能需要新的算法或实现。因此，支持某个任务的组件，也可能改变其他任务的委派程序构建难度。

Delegability Frontier（可委派性边界）描述的是：在给定资源与准确率要求下，系统能够可靠地委派哪些任务。委派式递归自我改进进一步追问：当系统不断求解任务，并将得到的能力用于后续开发时，这条边界会如何变化？

边界未必处处向外扩张。任务规则或外部接口变化，都可能使已有程序失效。系统必须识别过去的证据何时不再适用。声称取得进步时，也需要计入丢失的能力，以及维护成本上升的能力。

六让系统学会构建委派机制

一种可能的实现是学习式委派。强语言模型先生成候选的任务—程序配对，经过验证和筛选后，用这些数据训练一个较小的神经编译器，将任务规格和示例映射为可执行的委派程序。编译器生成的结果仍然需要通过验收。

这里存在两层摊销。实例层面，用程序替代同一任务上的重复推理；任务层面，用学到的编译器复用跨任务发现程序的经验。在训练编译器之前，可复用组件与验证器就可以支持第二层摊销。

因此，学习式编译器是实现委派式递归自我改进的一条路径，并非前提。核心要求是：积累的能力能够反馈到后续能力构建中。模型训练可以增强这种反馈，但它的贡献应当与工具和程序库带来的改善分别测量。

只在熟悉模板上成功，只能说明有限的迁移能力。新的组合、规则体系和任务家族提供了更强的检验。合成或验证失败时，系统可以回到强智能体，但这些调用仍然属于需要测量的成本。

七委派什么时候才划算？

即使程序正确，对于只出现一次的任务，构建它也可能不划算。设 G 为生成与初次验证成本，E 为每个实例的执行成本，L 为强智能体直接处理每个实例的成本，N 为程序需要修改之前处理的实例数。

直接推理的成本：N × L
基本委派成本：  G + N × E

基本盈亏平衡条件：
N × (L − E) > G

这些成本必须使用可比较的单位，并对应满足同一可靠性要求的系统。评估实际系统时，还应计入每个实例的调度与检查成本 O、每个实例的预期回退成本 F，以及复用期间的维护成本 M：

委派的总成本：
G + N × (E + O + F) + M

其中，F 包含回退调用的频率及成本，M 不重复计算已计入 G 的验证费用。直接执行的基线也应计入必要的检查与重试。编译器训练和共享程序库的构建成本，则需要在它们服务的任务之间进行核算。

递归改进可能降低未来的生成或验证成本，提高固定成本下的可靠性，或者让更多任务家族变得可行。这些是不同的结果。强模型调用次数减少，本身不能证明整个系统更便宜或更有能力。

八如何检验递归改进的主张？

一个有用的起点，是建立具有已知参考程序的可控任务序列，改变程序结构、规格完整性、执行成本，以及任务相对于现有程序库的新颖程度。参考程序能够在所测试的条件下确立解法存在；合成难度仍然需要通过具体合成器的成功率与预算来测量。

原有的委派比较仍然有用：强智能体直接执行、强模型生成委派程序，以及较小的学习式编译器生成委派程序。要检验递归性，还需要比较两类系统：一类只能用已有程序执行任务，另一类还能用它们构建和验证新的委派程序。

这些系统应从相同模型、初始工具、任务序列和资源核算规则出发。在若干检查点，使用固定的构建预算评估未见任务。比较冻结的初始程序库、只允许执行复用的积累程序库，以及完整的反馈闭环。通过移除可复用验证器或构建工具的消融实验，可以进一步定位改善来自哪些组件。

评估应区分已知任务的新实例、未见组合，以及需要未见规则或抽象的任务。用于选择或修复程序的输入必须与最终评估分开。如果加入编译器训练，应当将其作为独立的实验条件报告。

需要测量委派覆盖率、准确率、生成与验证成本、执行与监督成本、回退频率、人工干预及维护开销。最重要的是，随着先前经验积累，为新任务构建委派程序的成本和成功率如何变化。重复实验并改变任务顺序，有助于区分稳定效果与有利序列带来的偶然收益。

支持委派式递归自我改进的证据，应当是在计入全部成本之后，能够归因于这些可复用机制的后续能力构建改善。如果只有重复实例的执行变好了，我们证明了有价值的委派；如果构建过程没有改善，更强的递归主张就仍然缺乏支持。

九强智能体还需要做什么？

强智能体可以逐步把工作集中到发现抽象、处理陌生情况，以及改善负责常规任务的机制上。随着可靠的可执行能力增长，它的角色也随之变化。这个思路不要求每一项任务最终都能被编译。

有些任务变化太快，无法收回合成成本；有些任务缺乏足够明确的规格、成本可接受的检查器或合适的抽象。这些仍然是需要强智能体或人参与的原因，而他们的参与也需要相应的成功证据。

最初的“何时委派”，由此变成了关于系统如何发展的追问：系统能否把经验转化为可靠的可执行能力，再利用这些能力改善下一项能力的构建？委派式递归自我改进为这个拟议的反馈闭环命名。它的价值，应当由可靠任务覆盖范围的变化，以及实现这种变化的全部成本来判断。
